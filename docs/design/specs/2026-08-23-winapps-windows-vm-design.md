# WinApps: an on-demand Windows VM with Office, driven from dankMenu

**Date:** 2026-08-23
**Status:** designed

## Problem

Some things only exist on Windows. For this config that is Microsoft Office —
`onlyoffice-desktopeditors` (`modules/suites/school.nix`) covers reading and
light editing, but it is not Word, and coursework handed in through a
university portal is not the place to discover a layout difference.

The usual answer is a Windows VM you alt-tab into, which is a bad answer: a
whole second desktop for one application. WinApps is the better one. It runs
Windows headless, connects over RDP in RemoteApp mode, and each Windows
application arrives as its own native-looking window with its own launcher
entry. Word behaves like a Linux application that happens to render somewhere
else.

Three constraints shape everything below:

1. **It must not run at boot.** A Windows VM is 4 GB of RAM and a steady CPU
   tax. On the laptop that is a battery bill for something used a few times a
   week. The VM starts when asked and stops when done.
2. **Office must install itself.** A VM you have to hand-build once per machine
   is not part of a declarative config; it is a pet. First boot should end with
   Office present.
3. **Control belongs in the desktop, not a terminal.** This config already has
   a command tree bound to `Mod+Space` (`modules/desktop/dms/plugins.nix`,
   `dankMenu`). Starting and stopping the VM, and launching the applications,
   belong there.

## Decisions taken

Settled before design; not open:

- **Backend: Docker**, via `dockurr/windows`, not libvirt. See the next
  section.
- **Office 365 via the Office Deployment Tool**, run from the container's
  first-boot OEM hook.
- **Lifecycle: a systemd unit with `autoStart = false`**, started and stopped
  from dankMenu.
- **Every host gets it.** Both `omnibook` and `gamingpc` opt in, the same way
  both opt into `services.rclone`.
- **No activation circumvention.** The reference config
  (`celesrenata/nix-flakes`) carries `install-winkey.ps1` and
  `install-nevergreen.ps1`. Neither is reproduced here. Windows and Office are
  licensed by the user signing in.

## Why Docker and not libvirt

libvirt is the more capable host: snapshots, GPU passthrough, `virt-manager`,
and WinApps supports it as a first-class flavour. It loses on the one axis that
matters here.

The DMS plugin that surfaces this in the bar — `dockerManager`, in
`dms-plugin-registry` as `luckshiba-docker-manager` — talks to `docker`/`podman`
and nothing else. Under libvirt it would show an empty list, and the status
widget would have to be written from scratch. Under Docker it works with an
`enable = true`.

`dockurr/windows` also solves provisioning outright. It fetches the Windows ISO,
runs an unattended install from a generated `autounattend.xml`, and executes
anything it finds in `/oem` on first boot — which is exactly the hook that
constraint 2 needs. Reproducing that on libvirt means hand-writing the answer
file.

GPU passthrough is the real thing given up. For Office that is irrelevant, and
neither machine has a spare GPU to pass: `omnibook` has one integrated Xe3, and
`gamingpc`'s NVIDIA card is the desktop's own. Revisit only if something
graphics-heavy is ever added.

## Architecture

```
modules/services/winapps.nix          services.winapps.*         (new)
  ├── virtualisation.oci-containers.containers.windows           autoStart = false
  │     └── systemd unit docker-windows.service
  ├── /var/lib/winapps/oem/install.bat                           generated by Nix
  ├── sops secret winapps_vm_env  ──► container environmentFiles
  ├── polkit rule: wheel may start/stop docker-windows.service
  └── home.extraOptions
        ├── ~/.config/winapps/winapps.conf                       WAFLAVOR=manual
        ├── ~/.local/share/applications/<app>.desktop            generated from
        │                                                        ${winapps}/src/apps
        └── home.packages += winapps

modules/desktop/dms/plugins.nix       (edited)
  ├── dockerManager.enable = true                                status widget
  └── dankMenuRows += the `windows` subtree                      start/stop/launch

hosts/{omnibook,gamingpc}/default.nix (edited)
  └── services.winapps.enable = true
```

### The container

`virtualisation.oci-containers.containers.windows`, image `dockurr/windows`,
with `autoStart = false`. NixOS generates `docker-windows.service` either way;
`autoStart = false` simply leaves it out of `multi-user.target`. Nothing runs
until something starts that unit, which satisfies constraint 1 without a custom
unit or a timer.

Volumes:

| Host path | Container path | Purpose |
|---|---|---|
| `/var/lib/winapps/storage` | `/storage` | the VM's virtual disk |
| `/var/lib/winapps/oem` | `/oem` | first-boot scripts, see below |
| `~/Windows` | `/shared` | appears in Windows as `\\host.lan\Data` |

Ports are bound to loopback explicitly — `127.0.0.1:8006` for the web viewer and
`127.0.0.1:3389` for RDP. Docker's default publishes on all interfaces, which
would put an RDP host with a known password on every network the laptop joins.
The loopback prefix is not optional.

`extraOptions` carries `--device=/dev/kvm`, `--cap-add=NET_ADMIN`, and
`--stop-timeout=120`; the unit gets `TimeoutStopSec` above that, so Windows gets
a real chance to shut down cleanly rather than being killed mid-write.

Directories come from `systemd.tmpfiles.rules` rather than an activation script,
so they exist before the unit can ever run.

### Module options

`services.winapps` exposes the knobs that differ between machines, with defaults
sized for the laptop:

| Option | Default | Notes |
|---|---|---|
| `enable` | `false` | `mkEnableOption`, as everywhere else in this repo |
| `version` | `"11l"` | Windows 11 IoT Enterprise LTSC — smallest image that still has an RDP host. Home editions do not, and cannot be used |
| `ram` | `"4G"` | |
| `disk` | `"64G"` | Windows plus Office needs well over the reference config's 32G once updates land |
| `cores` | `4` | |
| `apps` | Word, Excel, PowerPoint, Outlook, OneNote | WinApps app ids; drives desktop-entry generation |
| `sharedDir` | `"${home}/Windows"` | host side of `\\host.lan\Data` |

`gamingpc` can raise `ram`/`cores` from its host file without touching the
module.

### Credentials

`dockurr/windows` takes `USERNAME` and `PASSWORD` as environment variables, and
WinApps needs the same pair in its config file to open the RDP session.

Anything in `oci-containers.<name>.environment` is rendered into the unit file
in the Nix store, which is world-readable. So the pair goes into a sops secret
holding a complete env file:

```
USERNAME=otis
PASSWORD=<generated>
```

wired in through `environmentFiles`, following the pattern already used for
`hass_token` in `modules/desktop/dms/plugins.nix`. The secret is `0400`, owner
`root`, since systemd reads it as root when starting the unit.

The same file cannot be read by `winapps.conf`, which is a plain shell file
sourced by the WinApps script as the user. Rather than duplicate the secret,
`winapps.conf` is written at home-manager activation time by substituting the
sops-decrypted values into a template — the same shape as the Anki secret merges
in `modules/suites/school.nix`. The generated file is `0600` in `~/.config`, not
in the store.

This is defence against casual exposure, not a strong boundary: the VM's RDP
port is loopback-only and its account is local to a disposable VM. The reason to
do it properly anyway is that a store-readable password is the kind of thing
that quietly becomes true elsewhere.

### First-boot provisioning

`dockurr/windows` runs anything it finds at `/oem/install.bat` once, as
administrator, at the end of the unattended install. The file is generated with
`pkgs.writeText` and copied in by tmpfiles, so it is part of the configuration
rather than a loose artefact.

It does three things, in order:

1. **RDP and RemoteApp registry setup.** Enable the RDP host
   (`fDenyTSConnections = 0`), open the firewall rule, and set
   `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Terminal Server\TSAppAllowList\fDisabledAllowList = 1`.
   That last key is what lets WinApps launch an arbitrary executable as a
   RemoteApp instead of only ones on an allow-list. Without it every
   `winapps <app>` fails, and the failure looks like a connection problem
   rather than a permissions one.
2. **Disable the console autologon** (`AutoAdminLogon = 0`). dockur's answer
   file signs the account in on the emulated console at every boot. Windows 11
   client editions allow one interactive session, so that console session holds
   the only slot and every WinApps logon has to take it over; the server asks
   the client to confirm the takeover (`LOGON_MSG_BUMP_OPTIONS`), FreeRDP has
   no way to answer that in RemoteApp mode, and the connection stalls and then
   dies mid-handover. What the user sees is "another user is still signed in,
   sign out there first" — with no other window to sign out of. Leaving the
   console at the sign-in screen makes the RDP session the only session.

   **This step only runs on a fresh install.** `/oem` executes once, at the end
   of setup, so a guest installed before this was added keeps autologning in.
   Fix an existing guest by signing the console out once (via the web viewer on
   `127.0.0.1:8006`) and then setting the key from an elevated shell in the
   guest:

   ```bat
   reg add "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon" /v AutoAdminLogon /t REG_SZ /d 0 /f
   ```
3. **Fetch the Office Deployment Tool** from Microsoft's official download URL
   and extract `setup.exe`.
4. **Run `setup.exe /configure configuration.xml`**, where `configuration.xml`
   is also Nix-generated: product `O365ProPlusRetail`, x64, Current channel,
   `Groove` and `Lync` excluded, display level none, `AcceptEULA` true.

Office then needs one interactive sign-in with a Microsoft 365 account, done
once inside the VM; the activation persists in `/storage` and therefore across
container restarts.

First boot is long — an unattended Windows install followed by an Office
download, plausibly 20 to 40 minutes. It is unattended, but it is not quick, and
progress is only visible through the web viewer on `127.0.0.1:8006`.

### WinApps

`github:winapps-org/winapps` is added as a flake input. It exposes
`packages.<system>.winapps` and `winapps-launcher` and no NixOS module, so this
config does the wiring itself. The package's wrapper already puts FreeRDP 3 on
`PATH` (verified: `freerdp-3.26.0`), so no separate `freerdp` entry is needed.

`~/.config/winapps/winapps.conf` sets:

```
RDP_USER / RDP_PASS   from the sops secret, at activation
RDP_IP="127.0.0.1"
WAFLAVOR="manual"
```

`WAFLAVOR="manual"` is the important line. Under `docker` the WinApps script
inspects, starts, and stops the container itself (`src/bin/winapps`, the
`WAFLAVOR` branches around lines 639-955), and expects to find a `compose.yaml`
it owns. That would put it in direct conflict with systemd over the same
container. `manual` short-circuits all of it — WinApps connects to `RDP_IP` and
does nothing else — leaving lifecycle wholly with systemd, which is what
constraint 3 wants anyway.

### Desktop entries

The upstream route is `winapps-setup`, which probes a running VM and writes into
`~/.local/share/applications` and `~/.local/bin`. That is imperative, needs the
VM up, and puts files outside home-manager's knowledge.

Instead the entries are generated in Nix. WinApps ships its application
definitions in the store at `${winapps}/src/apps/<id>/`, each with an `info`
file (`NAME`, `FULL_NAME`, `WIN_EXECUTABLE`, `CATEGORIES`, `MIME_TYPES`, `ICON`)
and an icon. The module reads those for each id in `services.winapps.apps` and
emits a `home.file` desktop entry per application, plus one `windows.desktop`
for the full remote desktop.

Consequences worth having: launchers exist after the first rebuild whether or
not the VM has ever booted, the MIME associations are declarative (so a `.docx`
opens in Word), and nothing is written outside home-manager's control.

The default set uses the `-o365` variants (`word-o365`, `excel-o365`,
`powerpoint-o365`, `outlook-o365`, `onenote-o365`) — those point at
`C:\Program Files\Microsoft Office\root\Office16\`, which is where the
Deployment Tool installs a click-to-run Office 365. The non-suffixed ids target
MSI installs at a different path and would not resolve.

### Bar widget and menu

`dockerManager` is in `dms-plugin-registry`, so `modules/desktop/dms/plugins.nix`
gains a plain `enable = true` alongside the others, with
`settings.terminalApplication` pointed at `ghostty` to match this machine
(the plugin defaults to `alacritty --hold`). It provides the status widget:
running/stopped, port mappings, logs, stop and restart.

It cannot provide *start*. NixOS runs oci-containers with `--rm`, so a stopped
container is a deleted container, and there is nothing for the plugin's start
button to act on. That is not a defect to work around — the container is
recreated from the unit each time, which is what makes it declarative. Start
therefore lives in dankMenu, alongside everything else.

The `dankMenuRows` list in `modules/desktop/dms/plugins.nix` gains a `windows`
subtree:

| Row | Behaviour |
|---|---|
| `windows.start` | `systemctl start docker-windows`; `disabled` when already active |
| `windows.stop` | `systemctl stop docker-windows`; `disabled` when inactive |
| `windows.word` … `windows.onenote` | `winapps <id>`; one row per entry in `services.winapps.apps` |
| `windows.desktop` | `winapps windows` — full remote desktop |
| `windows.viewer` | opens `http://127.0.0.1:8006`, for watching the install |
| `windows.shared` | opens the shared folder in Nautilus |

Rows are generated from the same `apps` option that drives the desktop entries,
so the two cannot drift.

The `when`/`disabled` shell snippets are evaluated by the plugin one level at a
time, so probing `systemctl is-active` there is cheap and only happens while the
`windows` submenu is open.

### Privilege

`systemctl start`/`stop` on a system unit needs root. Prompting through
`pkexec` on every start defeats the point of a menu entry.

A polkit rule scoped to exactly `docker-windows.service`, the `start` and `stop`
verbs, and the `wheel` group, returns `yes`. Nothing broader: not
`manage-units`, not other units, not other verbs. It is written in
`security.polkit.extraConfig` in the same module, so the grant lives next to the
thing it grants access to.

## Error handling

- **Docker not running.** `services.docker` comes from `suites.development`,
  which both hosts already enable. The module asserts on
  `config.services.docker.enable` rather than enabling Docker itself, so a host
  that drops the development suite fails at evaluation with a clear message
  instead of at runtime.
- **No KVM.** `--device=/dev/kvm` fails the container start loudly. Both hosts
  have it; nothing to do beyond letting the unit fail visibly.
- **VM not running when a launcher is clicked.** WinApps with
  `WAFLAVOR="manual"` fails the port check and sends a desktop notification.
  Acceptable: the menu shows state, and the failure is legible.
- **Office install fails on first boot.** The OEM script is idempotent enough to
  re-run by hand from inside the VM. Not automated — a retry loop around a
  40-minute download hides more than it fixes.
- **Secret missing.** The rebuild fails at sops decryption, before anything
  starts, which is the right time.

## Testing

- `just doctor` (`nix flake check --no-build` plus a dry build) for both hosts —
  catches option and generation errors.
- Inspect the generated `docker-windows.service`, `install.bat`,
  `configuration.xml`, and one desktop entry in the store before any boot.
- Confirm the unit is not in `multi-user.target`'s wants after a rebuild — that
  is constraint 1, and it is the thing most likely to silently regress.
- One real first boot on `omnibook`: watch `127.0.0.1:8006`, confirm Office
  appears, then `winapps word-o365`.
- Confirm `systemctl start docker-windows` from dankMenu does not prompt, and
  that `systemctl restart docker.service` from the same rule is still refused.

## Out of scope

- GPU passthrough.
- Any second VM, or WinApps' libvirt flavour.
- `winapps-launcher` (the tray applet) — the dankMenu subtree replaces it.
- Adobe applications, which the reference config also wires up.
- Automating the Microsoft 365 sign-in.
